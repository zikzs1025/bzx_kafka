瓶颈只有 fsync，不是 CPU、内存或磁盘带宽。 实测吞吐 ≈ 每批条数 ÷ (单次 fsync 延迟 × 每线程涉及的分区数)。 本机 fsync 约 1ms，500 条/批 × 每线程 5 个分区 → 约 10 万条/秒，与 300 万条长跑的 10.4 万吻合； 批量提到 2000 条 → 公式给 40 万，实测 36.2 万。这个式子可直接用于估算生产容量。
  • 数据完整性没有代价。17 次运行累计 1,090 万条 / 4.86 GB，回读行数逐条对齐、每行固定 31 列、隔离区始终为 0。
  • 批大小是最强杠杆。同硬件下 batch=100 为 3.16 万条/秒，batch=2000 为 36.2 万，差 11.5 倍——fsync 次数与批大小成反比。
  • 并发度必须跟上分区数。16 分区单线程仅 3.08 万条/秒（每批 fsync 16 次），换 3 线程后 12.7 万，提升 4.1 倍；这与默认 concurrency=3 恰好匹配。
  • fsync 只贵 10.1%。关掉它换来 10% 吞吐，代价是"断电可能丢已 ack 数据"，不值得。
  • 小文件有尖刺，但吞吐不降。5000 行/文件时 p99 从 12.2ms 跳到 90.2ms（7 倍），文件数 16 → 48，FTP 交互次数同步变成 3 倍。

为什么 100 万条比 50 万条慢？不是衰减，是页缓存。50 万条（239 MB）基本被 32 GB 内存的吸收， fsync 命中缓存；100 万条（478 MB）开始触碰真实落盘，吞吐回落到 11.4 万；300 万条（1.43 GB）稳定在 10.4 万。 生产环境请以 10 万条/秒作为规划基准，36 万只是短时爆发的上限。

除了"跑得快"，更关心"跑得稳"：内存是否泄漏、背压是否生效、长跑是否衰减。

6调参建议

基于实测，只改两个参数就能拿 2.85 倍收益；其余保持默认。

参数当前建议理由（实测依据）
kafka.consumer.max-poll-records 5001000 ~ 2000 吞吐 12.7 万 → 36.2 万条/秒。单批内存仅 2000×478B ≈ 1MB，代价可忽略
kafka.consumer.concurrency 3≥ 分区数 / 6 16 分区单线程 3.08 万 → 3 线程 12.7 万（4.1 倍）。线程过少会让每批 fsync 次数暴涨
file.records-per-file 50000保持 50000 降到 5000：p99 从 12.2ms → 90.2ms，文件数 16 → 48（FTP 交互次数 3 倍）
file.fsync-per-batch true保持 true 关掉只多 10.1% 吞吐，却失去"已 ack 必落盘"的保证
kafka.consumer.max-poll-interval-ms 300000保持 300000 最坏单批 186.3ms，余量两个半数量级，无需调整
容量估算：目标 QPS ≈ batch ÷ (fsync_ms × 每线程分区数)。 若上游峰值 5 万条/秒、16 分区、fsync 1ms，取 batch=1000、concurrency=3（每线程约 5 分区）， 理论 20 万条/秒，留 4 倍余量。若峰值超过 20 万条/秒，优先加批量（batch=2000）， 其次加线程/分区；不要靠缩小文件去换并行度——那只会把 p99 拉高。

7方法论与局限

说清楚测了什么、没测什么，避免把本机数字当成生产承诺。

  • 测的是本服务的核心链路，不是 Kafka 客户端。用 ConsumerRecord 直接构造消息，绕过 broker 与网络；FTP 用"只校验可读、不实际传输"的桩。这样排除网络与对端磁盘，只衡量渲染 + 写盘 + 封盘 + 备份能力。
  • 没测：真实 broker 的 rebalance 与分区再均衡、字节反序列化开销、真实 FTP 传输耗时与超时重试、多实例同组消费。
  • 环境是笔记本：Ultra 5 + 消费级 NVMe。生产若是机械盘或网络存储，fsync 延迟会从 ~1ms 升到 5~15ms，吞吐按公式等比例下降——这正是"别把 12.7 万当承诺"的原因。
  • 数据是合成的：478 B/条、31 字段齐全、含中文与长整型，但无超长字段（>64KB）与极端脏数据。
  • JVM 已预热：每次先跑 1 万条热身再计时，避免把 JIT 编译成本算进吞吐。
  • 指标口径修正过：早期版本用"总耗时 ÷ 总批次"当均值，多线程下把并发误算成串行（均值 3.84 小于 p50 9.13）；现已改为对每批延迟求平均，本报告全部数据来自修正后的版本。

8复现方式

压测程序在 src/test/java/.../bench/LoadTestHarness.java，不参与 mvn test（类名不匹配 surefire 规则）。

# 1. 编译（含压测程序）
mvn -o test-compile

# 2. 从 fat jar 抽取依赖，组装离线 classpath
python -c "import zipfile,os;z=zipfile.ZipFile('target/kafka-file-loader.jar');os.makedirs('target/lib',exist_ok=True);[open('target/lib/'+os.path.basename(n),'wb').write(z.read(n)) for n in z.namelist() if n.startswith('BOOT-INF/lib/') and n.endswith('.jar')]"

# 3. 推荐配置：16 分区 / 3 线程 / 500 条一批 / 50 万条
java -Xms512m -Xmx512m -cp "target/classes;target/test-classes;target/lib/*" \
  com.example.kafkaloader.bench.LoadTestHarness \
  --records=500000 --partitions=16 --threads=3 --batch=500 \
  --per-file=50000 --fsync=true --label=D-p16t3-500k --keep=false

# 4. 验证背压（预期抛 BackpressureException）
java -cp "target/classes;target/test-classes;target/lib/*" \
  com.example.kafkaloader.bench.LoadTestHarness \
  --records=200000 --partitions=16 --threads=3 --per-file=5000 \
  --max-pending=2 --label=J-backpressure --keep=false

每次运行输出 target/perf/run-<label>.json（含全部指标与校验结果）； --keep=true 保留生成的文件供人工抽查；target/perf/summarize.py 汇总中位数并生成本报告的数据源。
